# 架构说明

## 1. 分层

```
┌──────────────────────────────────────────────────────────────┐
│ 表现层   WPF 桌面程序（推荐）        网页控制台（可选）      │
└───────────────────────┬──────────────────────────────────────┘
                        │ 共用 OrSend.Shared 的运行时
┌───────────────────────▼──────────────────────────────────────┐
│ 托管层   EngineHost 拉起 orsend.exe   EngineClient 收发请求  │
└───────────────────────┬──────────────────────────────────────┘
                        │ 本地 JSON-RPC（127.0.0.1:7400+）
┌───────────────────────▼──────────────────────────────────────┐
│ 编排层   OrSendApp：读配置 → 装配组件 → 注册控制命令         │
├──────────────────────────────────────────────────────────────┤
│ 业务层   PortForward/PortMapping/TunnelServer/TunnelClient   │
├──────────────────────────────────────────────────────────────┤
│ 引擎层   RelayEngine（监听→拨号→双向转发）                   │
├──────────────────────────────────────────────────────────────┤
│ 网络层   EventLoop(poll) / TcpConnection / TcpListener       │
├──────────────────────────────────────────────────────────────┤
│ 基础层   Socket 兼容层 / JSON / Logger / Endpoint            │
└──────────────────────────────────────────────────────────────┘
```

C++ 引擎负责全部数据面，C# 只负责配置与观测，两者通过本地控制接口解耦：

- 引擎可以单独跑（命令行、systemd、Windows 服务）
- 界面可以晚于引擎启动，也可以中途重启，不影响正在转发的流量
- 界面挂掉不会中断隧道
- 桌面端与网页端共用 `OrSend.Shared` 里的同一套运行时，行为一致

## 2. 线程模型

整个引擎只有 **一个事件循环线程**：

```
main thread                 loop thread
   │                            │
   ├─ 读配置 / 建组件            ├─ poll() 等待 fd 事件
   ├─ 启动监听 fd ────────────►  ├─ 派发读/写/错误事件
   ├─ loop.Run()（新线程）       ├─ 触发定时器
   └─ Wait() 阻塞在条件变量      └─ 执行 Post 过来的任务
```

规则：

- 所有 fd 的注册、注销、读写回调都在 loop 线程执行，**没有数据竞争**
- 其它线程只能通过 `EventLoop::Post()` 投递闭包
- `poll()` 的等待上限是 50ms，保证投递的任务能在 50ms 内被执行

为什么不用「一连接两线程」？内网穿透里一条控制连接上会复用几百条 stream，
如果每条 stream 两个阻塞线程，线程数会瞬间爆炸。reactor + 非阻塞 IO 是唯一可行的路子。

## 3. 一次内网穿透请求的完整链路

```
浏览器          TunnelServer                TunnelClient(agent)        内网服务
  │                  │                            │                      │
  │ TCP connect      │                            │                      │
  ├─────────────────►│ accept                     │                      │
  │                  │ 分配 streamId=7            │                      │
  │                  │ TUNNEL_OPEN(7,"web")       │                      │
  │                  ├───────────────────────────►│                      │
  │                  │                            │ 拨号 127.0.0.1:8080  │
  │                  │                            ├─────────────────────►│
  │                  │                            │◄────── 连接建立 ──────┤
  │                  │   TUNNEL_OPEN_ACK(7,ok)    │                      │
  │                  │◄───────────────────────────┤                      │
  │  （此时才开始读公网侧数据，天然背压）           │                      │
  │ HTTP GET /       │                            │                      │
  ├─────────────────►│ DATA(7,payload)            │                      │
  │                  ├───────────────────────────►│                      │
  │                  │                            ├─────────────────────►│
  │                  │                            │◄───── 200 OK ────────┤
  │                  │ DATA(7,payload)            │                      │
  │◄─────────────────┤◄───────────────────────────┤                      │
  │                  │                            │                      │
  │ close            │ CLOSE(7)                   │                      │
  ├─────────────────►├───────────────────────────►│ close                │
```

关键设计：**公网侧的 socket 在收到 ACK 之前不 `Start()`**。
数据留在内核接收缓冲区里，由 TCP 窗口自然限流，不会在用户态堆积内存。

## 4. 转发引擎

`RelayEngine` 一条规则对应一个 `RuleRuntime`：

```
RuleRuntime
├── TcpListener            监听 fd
├── targets[]              TargetState { up, probing, active, lastError }
├── cursor                 轮询游标
├── stats                  连接数 / 活跃 / 失败 / 字节
└── sessions{}             活跃会话
```

新连接进来时：

1. 创建 `Session`，**先不启动读**
2. 按策略挑一个目标（`roundrobin` / `leastconn` / `random` / `failover`）
3. 非阻塞 connect，带超时
4. 成功 → 双向接线 → 启动读；失败 → 标记目标 down，换下一个目标重试
5. 任一侧关闭 → 关闭另一侧，回收统计

健康检查对每个目标周期性发起一次短连接探测，失败超过一次即标记 down，
后续新连接自动跳过。目标恢复后自动重新纳入。

**全部目标都被标记 down 时会退化成"盲试一次"**：否则目标刚恢复，规则还要等到
下一个探测周期才能用，白白多出一段不可用时间。

## 5. 关闭连接：数据不能丢

关闭是这类代理最容易出 bug 的地方，这里有两道保险：

**① `POLLHUP` 必须先读干净再关。**
对端"把数据发完并关闭"时，`poll` 经常一次同时上报 `POLLIN | POLLHUP`。
如果见到 `POLLHUP` 就直接关，接收缓冲里那段数据就没了——现象是响应只剩响应头，
或者 512KB 的响应少了最后一截。所以 `TcpConnection::HandleEvent` 在错误分支里
先 `HandleRead()`（读到 EOF 会自行关闭），再尝试刷写，最后才关。

**② 关闭要"刷完再断"，而不是 `CloseNow()`。**
`CloseNow()` 会清空写缓冲。高并发下 `send` 很可能只写出去一部分，剩下的还在缓冲里，
此时一个 `CloseNow()` 就把尾巴丢了。统一走 `ConnectionReaper::Retire()`：

```
停掉回调  →  Close()（先刷写，刷完才真正 close，5 秒兜底）
          →  连接对象放进 draining_ 继续持有
          →  下一轮事件循环再释放（不能在连接自己的回调栈里析构它）
```

第 3 步是必须的：`TcpConnection` 的析构函数会直接 `close(socket)`，
如果 `Retire()` 之后没有任何强引用，对象立刻析构，前面刷写就白做了。

## 6. 背压

`TcpConnection` 内置水位控制：

- 发送缓冲超过 `highWaterMark`（1MB）→ 暂停读对端
- 缓冲排空到 `lowWaterMark`（256KB）→ 恢复读

这样一侧是慢速客户端、另一侧是快速服务器时，内存不会无限增长，压力会沿 TCP 窗口传回源头。

## 7. 内存与生命周期

C++ 里最容易出事的是对象生命周期，这里统一用三条规则：

1. **连接对象由 `shared_ptr` 持有**，回调里一律用 `weak_ptr` 或「id + 查表」，避免循环引用
2. **异步操作前先把对象放进容器**（如 `streams_[id] = stream`），否则 `weak_ptr` 会立刻失效
3. **回调里不直接持有会失效的裸指针**，规则名 / 会话 id 这类轻量键更安全

## 8. 为什么用 poll 而不是 select

`select` 在 Windows 上有 `FD_SETSIZE`（默认 64）的硬限制，且需要把 fd 集合每次重建。
`WSAPoll` / `poll` 没有这个限制，语义也更清晰（`POLLIN` / `POLLOUT` / `POLLERR`）。
仍然是一个线程 + 一次系统调用处理全部 fd，属于同一个多路复用家族。

## 9. 扩展方向

- IPv6 / UDP 转发：`Endpoint` 里加 family 字段，`RelayEngine` 增加 UDP 分支
- 多线程 loop：每个 loop 一个线程，accept 后按 fd 取模分发（需要跨 loop 投递）
- TLS：在 `TcpConnection` 之下加一层 OpenSSL BIO
- 鉴权升级：token → HMAC 挑战应答，避免明文口令
- 配置热加载：`ControlServer` 加 `config.reload`
